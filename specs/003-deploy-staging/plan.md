## 1. Visión general

- Un único workflow `.github/workflows/ci.yml` con dos jobs:
  - **`check`** (push a main y PR hacia main): install con lockfile congelado → navegador → lint → format:check → **una sola build** de las dos apps → `pnpm test` y Lighthouse **sobre esa build** → (solo en push) sube `apps/web/dist` como artefacto.
  - **`deploy`** (solo push a main, `needs: check`, entorno `staging`): comprobación previa (secretos presentes y commit = punta de main) → descarga la misma `dist` → prepara la copia de staging (copia + archivo de cabeceras) → `wrangler deploy` → smoke test contra la URL compuesta con el secreto del subdominio.
- La lógica nueva va en funciones puras con tests en Vitest (principio 3): comprobaciones del smoke test y reintentos con reloj inyectado, archivo de cabeceras de staging, comprobación previa, detector de filtraciones y detector de `noindex` en la build. Los CLI son capas finas que leen disco, entorno o red y llaman a esas funciones.
- La paridad con Cloudflare se comprueba primero en local con `wrangler dev` (sin cuenta ni token) y se confirma en el primer despliegue real, que hace el usuario tras el alta (parada final, sección 10).

## 3. Workflow (`.github/workflows/ci.yml`)

```
name: CI
on:
  push:          { branches: [main] }
  pull_request:  { branches: [main] }
permissions: { contents: read }            # workflow level; no job adds write permissions

jobs:
  check:
    runs-on: ubuntu-24.04
    concurrency: { group: check-${{ github.head_ref || github.ref }}, cancel-in-progress: true }
    env: { CI: true, ASTRO_TELEMETRY_DISABLED: 1, COREPACK_ENABLE_DOWNLOAD_PROMPT: 0 }
    steps:
      - checkout (SHA, persist-credentials: false)
      - setup-node (SHA, node-version-file: .node-version)
      - corepack enable && pnpm --version && node --version        # RF-30: versions in the log
      - pnpm install --frozen-lockfile                              # RF-30
      - pnpm browsers:install --with-deps                           # RF-31 (Linux system deps)
      - pnpm lint
      - pnpm format:check
      - pnpm build                                                  # the only build of the run (RF-11)
      - pnpm test            env PREBUILT_DIST=1                    # Vitest + check-browser + Playwright on that build
      - node scripts/check-browser.mjs && pnpm --filter web quality # Lighthouse on that same dist
      - if push: upload-artifact (SHA) name web-dist, path apps/web/dist, retention-days 1, if-no-files-found error

  deploy:
    needs: check
    if: github.event_name == 'push' && github.ref == 'refs/heads/main'
    runs-on: ubuntu-24.04
    environment: staging                     # name only, never `url` (RF-40)
    concurrency: { group: deploy-staging, cancel-in-progress: false }   # serial, never cancelled (RF-33)
    env: { WRANGLER_SEND_METRICS: false, COREPACK_ENABLE_DOWNLOAD_PROMPT: 0 }
    steps:
      - checkout (SHA, persist-credentials: false)
      - id: preflight  node scripts/staging/preflight.mjs           # env: the 3 secrets; RF-4, RF-37
      - (if ready) setup-node, corepack enable, pnpm install --frozen-lockfile
      - (if ready) download-artifact (SHA) web-dist → apps/web/dist                 # no build step (RF-11)
      - (if ready) pnpm --filter web staging:copy  with VERSION=${{ github.sha }}   # RF-10
      - (if ready) pnpm --filter web staging:deploy  env CLOUDFLARE_API_TOKEN, CLOUDFLARE_ACCOUNT_ID, CF_WORKERS_SUBDOMAIN
      - (if ready) pnpm smoke --version ${{ github.sha }}  env CF_WORKERS_SUBDOMAIN   # mandatory, no continue-on-error, no rollback step (RF-5)
```

Notas:

- **Concurrencia (resuelve el menor b de QA).** La concurrencia va **por job**, no por workflow, en dos grupos separados: `check-<rama>` cancela el `check` antiguo de la misma rama; `deploy-staging` es común, serie y sin cancelación. Un push nuevo nunca cancela un `deploy` en curso porque está en otro grupo; si el `check` antiguo se cancela, su `deploy` no arranca (`needs`). GitHub sustituye un `deploy` _pendiente_ por el más nuevo, que es lo deseado. Alternativa descartada: concurrencia a nivel de workflow con `cancel-in-progress: true`, que cancelaría también un despliegue a medias.
- **Enmascarado.** El subdominio es secreto: GitHub lo sustituye por `***` en todo el registro, así que la URL que imprima wrangler sale como `agencymac-staging.***.workers.dev`. El smoke test compone la URL a partir del secreto y solo imprime rutas relativas (RF-12, RF-27, RF-39). No se pasan la URL ni los secretos como outputs de pasos.
- **Secretos solo en `deploy`**, y solo en los pasos de `preflight`, `staging:deploy` y `smoke` (RF-35). PRs de forks: el job no corre y GitHub no les da secretos; otras ramas: el entorno solo admite main.
- **Comprobación previa.** `preflight` compara `github.sha` con la punta remota de main (`git ls-remote`, repo público, sin token). Si no coincide o falta algún secreto, los pasos siguientes se saltan con `::warning::` y el job queda en verde (RF-4, RF-37).

## 4. Decisiones técnicas

- **P1. wrangler como devDependency de `apps/web`** (N1) invocado con `pnpm`, en lugar de `wrangler-action`. Menos código de terceros junto al secreto, versión en el lockfile y paridad comprobable en local con `wrangler dev`. Pendiente de aprobación.
- **P2. `yaml` para los tests del workflow** (N2). Pendiente de aprobación.
- **P3. Node con `setup-node` + `node-version-file: .node-version` y pnpm con corepack** (versión de `packageManager`), sin `pnpm/action-setup`. Así `engineStrict` y `preinstall` se comportan igual que en local. Sin caché del almacén de pnpm en esta spec (RNF-7 es orientativo); se puede añadir después.
- **P4. Copia de staging en `apps/web/.staging/`** (ignorada por git), y `wrangler.json` apunta ahí. La `dist` nunca se modifica, ni en local ni en el runner; la copia es `dist` + `_headers`. Alternativa descartada: escribir `_headers` dentro de la `dist` descargada (funciona en el runner, pero en local ensuciaría la build que prueban Playwright y Lighthouse).
- **P5. `wrangler.json` (JSON puro) en lugar de `wrangler.jsonc`**: el test lo lee con `JSON.parse`, sin otra dependencia. Las explicaciones van en `apps/web/AGENTS.md`. Alternativa descartada: `.jsonc` con comentarios, que obligaría a un parser JSONC.
- **P6. `html_handling: "auto-trailing-slash"`**: reproduce `/en` → `/en/` y sirve `/en/` desde `en/index.html`. Observado en T5: Cloudflare usa **307** en `/en`, `/index.html` y `/404.html`, y sirve `/404` con 200. RP-4 se activó y el usuario aceptó ese comportamiento (D17 de la spec); el servidor local lo copia (D6).
- **P7. Una sola build en el CI con `PREBUILT_DIST=1`** leída por `playwright.config.ts`, y Lighthouse con `pnpm --filter web quality` (sin el `build` del script raíz). `pnpm test` y `pnpm quality` en local no cambian. Alternativa descartada: cambiar los scripts raíz con condicionales de shell (frágil con `shellEmulator` en Windows).
- **P8. Comprobación de `noindex` de la build como e2e** (`dist-clean.spec.ts`) con lógica pura en Vitest. Así siempre corre después de la build (local y CI). Alternativa descartada: un test Vitest sobre `dist`, que fallaría o se saltaría si aún no hay build.
- **P9. Versión por cabecera `X-Staging-Version`** con el SHA completo (D13 de la spec); el smoke test reintenta cada 10 s hasta 180 s.
- **P10. Runner fijo `ubuntu-24.04`** (no `ubuntu-latest`), coherente con versiones exactas. Lighthouse en CI con `--no-sandbox` solo cuando `CI` está definido.
- **P11. Telemetría de wrangler desactivada** (`WRANGLER_SEND_METRICS=false`) en scripts y workflow, como la de Astro.

waitForVersion({ fetchVersion, expected, now, sleep, limitMs = 180_000, intervalMs = 10_000 }):
  start = now()
  loop:
    got = await fetchVersion()                        // value of X-Staging-Version or null
    if got === expected → return { ok: true }

## 6. Detector de filtraciones (resuelve el menor a de QA)

`findLeaks` aplica tres reglas a cada archivo versionado de texto:

- **(a) Hosts `workers.dev`.** Falla cualquier coincidencia de `[a-z0-9-]+(\.[a-z0-9-]+)*\.workers\.dev`. Los marcadores admitidos lo son **por construcción**, porque el carácter justo antes de `.workers.dev` no es una letra, cifra ni guion: `agencymac-staging.<subdominio>.workers.dev`, `<subdominio de la cuenta>.workers.dev` y `*.workers.dev`. Regla para la documentación y la spec: escribir siempre la parte variable entre `<…>` o como `*`. La spec ya usa esas formas; `docs/staging.md` y los `AGENTS.md` también. El nombre del Worker seguido directamente de `.workers.dev`, sin subdominio, también falla, a propósito.
- **(b) Secretos con valor.** Para `CLOUDFLARE_API_TOKEN`, `CLOUDFLARE_ACCOUNT_ID` y `CF_WORKERS_SUBDOMAIN`: falla una línea `NOMBRE\s*[:=]\s*<valor>` cuyo valor no sea `${{ secrets.NOMBRE }}`, vacío, ni un marcador entre `<…>` (con o sin comillas). Las menciones del nombre en texto (p. ej. "`CLOUDFLARE_API_TOKEN`") no fallan. Los tests usan valores `"<token>"` o los construyen en tiempo de ejecución.
- **(c) Archivos.** Falla cualquier ruta versionada `.env`, `.env.*` (salvo `.env.example`), `.dev.vars` o dentro de `.wrangler/`.

No busca cadenas hexadecimales genéricas: el lockfile y los SHA de las acciones no dan falsos positivos.

## 7. Alta inicial (`docs/staging.md`) — resuelve el menor c de QA

Pasos para el usuario (ningún agente los hace, RP-1), en este orden:

1. Crear la cuenta gratuita de Cloudflare y activar el subdominio de `workers.dev` de la cuenta. **Aviso:** elegir un subdominio largo y poco común (p. ej. no `agency`, `mac`, `test` ni palabras frecuentes): GitHub enmascara ese texto en **todo** el registro, y un subdominio corto o común taparía con `***` partes normales de los registros y los haría ilegibles. Anotarlo solo en un lugar privado.
2. Crear un token de API personalizado: solo `Account → Workers Scripts → Edit`, limitado a esa cuenta, con caducidad de 12 meses como máximo; anotar la fecha de renovación en un lugar privado. Riesgo aceptado (D16): podrá editar cualquier Worker de la cuenta; se revisa al pasar a producción.
3. En GitHub, **antes de subir a main el workflow**: Settings → Environments → New environment `staging` → Deployment branches and tags → Selected branches → solo `main`. Si GitHub ya lo creó automáticamente, revisarlo y restringirlo antes del paso 4.
4. Añadir en el entorno `staging` (no en el repositorio) los secretos `CLOUDFLARE_API_TOKEN`, `CLOUDFLARE_ACCOUNT_ID` y `CF_WORKERS_SUBDOMAIN`. Crear los secretos equivale a autorizar el despliegue (RP-2).
5. Consultar la URL de prueba en el panel de Cloudflare (Workers & Pages → `agencymac-staging`), nunca en los registros ni en el repo.

## 11. Riesgos

- **RP-4 (resuelto en T5).** Con `html_handling: "auto-trailing-slash"`, `wrangler dev` sirvió `/404` y `/en/404` con 200 y redirigió `/404.html` y `/en/404.html` con 307. El usuario lo aceptó (D17); sin código de Worker. Queda el riesgo de que el despliegue real difiera de `wrangler dev`: se trataría con RP-3.
- **`X-Robots-Tag` en las 3xx**: si las reglas de `_headers` no se aplican a las redirecciones de Cloudflare, RF-25 falla → RP-4.
- **`wrangler dev` frente a producción**: el motor local es el mismo, pero puede haber diferencias; la confirmación definitiva es el primer despliegue (parada final, RP-3).
- **Scripts de instalación de `workerd` bloqueados por pnpm 12**: se autoriza solo lo necesario en `pnpm-workspace.yaml` (cubierto por la aprobación de N1). Si no basta, se para.
- **Permiso del token**: si `wrangler deploy` necesita algo más que `Workers Scripts: Edit` (p. ej. leer el subdominio de la cuenta), falla el paso en rojo; se para y se ajusta el alta con el usuario, sin ampliar permisos por defecto.
- **Lighthouse en Ubuntu**: el sandbox de Chromium puede no arrancar → `--no-sandbox` solo en CI. El ruido del runner se resuelve relanzando, nunca bajando umbrales.
- **Lo que imprima wrangler**: el subdominio queda enmascarado; si wrangler mostrara otro dato de cuenta (nombre, correo), se revisa el registro en la parada final (RF-39) y se para si aparece algo reservado.
- **Carrera entre la comprobación previa y el despliegue**: la ventana es de segundos y los despliegues van en serie; el siguiente push corrige cualquier desfase.
- **Procesos huérfanos en Windows** en 4322 u 8787: matarlos antes de los tests (AGENTS.md).
